# Construction live-wiring — implementation blueprint

_Generated 2026-06-24 from the construction-wiring-design workflow (5 agents). Reference for wiring the verified construction evaluator into the live Toolkit._

## Approach

Wire construction in-process (no HTTP): the Toolkit's pillar calculators already produce rawStats, so add a single mapper + a store branch that calls the pure engine directly. Concretely:

(1) DIRECT-IMPORT THE ENGINE. vite.config.ts already defines alias `@api -> ../api` and lists ../api in `server.fs.allow`, and `calculateConstructionScorecard`/`ConstructionScoringInput` in apps/api/pipeline/constructionScoring.ts is a pure, dependency-free function (verified: no DB/Node I/O). So import it in the Toolkit: `import { calculateConstructionScorecard, type ConstructionScoringInput, type ConstructionScorecardOutput } from '@api/pipeline/constructionScoring'`. No new API call; matches the existing pattern where the store already imports the CalculatorConfig type cross-dir.

(2) NEW MAPPER FILE: apps/web/Toolkit/src/lib/calculators/construction-map.ts exporting `buildConstructionScoringInput(state: PillarState): { entityType: string; input: ConstructionScoringInput }`. It runs the existing pillar calculators to get rawStats — calculateOwnershipScore(state.ownership,cfg), calculateManagementScore(state.management,cfg,eapProvince), calculateSkillsScore(state.skills,cfg,eapProvince), calculateProcurementScore(state.procurement,cfg), calculateEsdScore(state.esd,npat,cfg)+calculateSedScore — then maps each indicator inputKey. Three rules the mapper MUST enforce per the engine switch (constructionScoring.ts:185-273): (a) `percentage`/`bonus_threshold`/`net_value`/`eap_percentage` keys take WHOLE-NUMBER percent, so multiply the 0-1 ownership/management rawStats fractions by 100 (boardBlackPct, execBlackPct, blackVotingPercentage, etc.); (b) `percentage_of_npat|leviable|tmps` keys take RAW recognised ZAR numerators (pass skills.rawStats.blackSpend, procurement.rawStats.empoweringSpend/spendEME/spendQSE/blackOwned51Spend/designatedGroupSpend, esd.sdSpend, sed.actualSpend directly — engine divides); (c) `evidence` keys take booleans. Ratio-derivables computed in the mapper: skills.bursaries = bursarySpend/blackSpend*100; skills.disabilities/cat_abcd as count ratios. entityType resolves from client.scorecardType: 'Contractor'->construction_contractor, 'BEP'->construction_bep, else (QSE under CONSTRUCTION sector)->construction_qse; set input.subSector from scorecardType for the QSE designated-groups target override.

(3) STORE BRANCH. In apps/web/Toolkit/src/lib/store.ts loadCalculatorConfig (lines 1348-1442), add `if (client.sectorCode === 'CONSTRUCTION') { set bundled CONSTRUCTION_CALCULATOR_CONFIG (a new minimal config exposing pillar maxPoints O/MC/S/ESD/SED so assertSectorConfigLoaded passes); get()._recalculateAll(); return; }` BEFORE the fetchSectorCalculatorConfig fallback. Then in calculateScorecard (lines 553-874) add an early branch: when sectorCode==='CONSTRUCTION', call buildConstructionScoringInput + calculateConstructionScorecard and adapt ConstructionScorecardOutput.elementScores into the existing ScorecardResult shape (ownership/managementControl/skillsDevelopment/[ESD split into supplierDevelopment+enterpriseDevelopment or a single esd pillar]/socioEconomicDevelopment, total, achievedLevel via pointsToLevel). Store the raw ConstructionScorecardOutput on a new scorecard.construction field for the detailed indicator view. Add a CONSTRUCTION sector-config + isConstructionSector helper file at apps/web/Toolkit/src/lib/sectors/construction.ts mirroring rcogp-qse.ts.

(4) RESULTS VIEW. Extend apps/web/Toolkit/src/pages/Scorecard.tsx (and/or a new ConstructionScorecard.tsx) to render the per-indicator ConstructionScorecardOutput (indicator code/name/weight/target/achievedPoints/status/missingFields/recommendation already on each IndicatorResult), grouped by the 5 elementScores, plus the missingFieldSummary list so the gaps surface in the UI.

New input fields (sections 2/5) are added to the pillar pages + types.ts so the mapper can read them; gender rule (section 3) lives entirely in the mapper since the engine does no gender math.

## Risks / go-live gates

- UNIT-CONVERSION BUGS are the highest risk: ownership/management rawStats are 0-1 fractions (must *100) while percentage_of_* keys take RAW ZAR (must NOT be percentaged). Mixing these silently produces near-zero or capped-max scores. The mapper must label every key by calculation kind and the golden test must assert both paths.
- Direct @api import: the engine is pure today, but if anyone later adds a Node-only import (fs/db/logger) to constructionScoring.ts or its constructionIndicators.ts dependency, the Toolkit browser build breaks. Keep the import surface to those two pure files only (or relocate them into a shared/ package).
- Threshold mismatches need RECOMPUTE not rawStats reuse: pp_35_black_women_owned (Toolkit 30% vs 35% construction), bonus_black_women_51 (need 51% women threshold), possibly bonus_designated_groups_51 (51% designated). Reusing blackFemaleOwned30Spend/designatedGroupSpend over-counts; the mapper must re-sum recognised supplier spend at the correct ownership threshold from procurement suppliers[].
- TMPS lives on procurement.tmps (types.ts:328) NOT on client — financials.totalMeasuredProcurementSpend must be sourced from procurement state or all 7 ESD PP indicators return missing_data.
- BEP professional-registration ownership discount (>50% ownership by prof-registered execs) is unimplementable from current Shareholder data; without the new isProfRegisteredExecOwner flag the BEP ownership %s are over-stated (un-discounted). Must be flagged to the verifier as a known approximation until the flag ships.
- Gender A=(B/1.3)+C is entirely in the mapper; the engine's bonus_threshold/percentage do no gender math. If a future engine upgrade adds gender adjustment, the mapper would double-apply it — guard with a single source of truth and a test.
- Several 'derivable' skills indicators (african_eap, cat_abcd, disabilities, new_entrants EI) are only derivable once new aggregates are EXPOSED in ownership.ts/skills.ts rawStats; until then they behave as new-input-needed. Decide per indicator whether to expose an aggregate or collect a manual %, and keep the choice consistent across QSE/Contractor/BEP.
- Config/UNVERIFIED warning (per MEMORY construction-sector-model + qse.skills.spend_black_secondary TODO and pp_eme/pp_qse empowering-restriction caveats): some targets/sub-sector configs are not expert-signed-off; wiring them live without verifier sign-off risks shipping wrong scores. Gate go-live on Zoleka/verifier confirmation of the flagged targets.
- scorecardType collision: construction QSE and RCOGP QSE share scorecardType='QSE'; routing to construction_qse MUST also gate on sectorCode==='CONSTRUCTION', else RCOGP QSE clients get mis-routed.
